# 0004. Транзакция продажи и блокировки

**Статус:** принято
**Дата:** 2026-10-05

## Контекст

ТЗ требует, чтобы два параллельных чека не продали один и тот же остаток, и чтобы при
любой ошибке состояние откатывалось целиком. Критерий приёмки 4: два параллельных
запроса за последнюю единицу — один 201, второй 409.

## Решение

`POST /sales` выполняется в одной транзакции (`READ COMMITTED`):

1. `SELECT … FOR UPDATE` по товарам, отсортированным по `id`, и по строке покупателя.
2. Проверка остатков по заблокированным значениям.
3. Расчёт сумм чистой функцией `bonus.Calculate`.
4. Вставка `sales` и `sale_items` (с копией названия и цены).
5. `UPDATE products SET stock = stock - $qty WHERE stock >= $qty`.
6. Обновление бонусов покупателя.

Любая ошибка откатывает транзакцию целиком.

## Почему именно так

- Сортировка id перед `FOR UPDATE` обязательна: без неё две продажи, пересекающиеся по
  двум товарам, могут взаимно блокироваться и упираться в deadlock.
- `bonus.Calculate` — чистая функция без БД, поэтому правила бонусов тестируются
  отдельно, а транзакция отвечает только за согласованность.
- Двойная проверка остатка (в Go и в `WHERE`) защищает от расхождения, если между чтением
  и записью изменится состояние строки.

## Как это проверяется

`tests/sales_race_test.go` поднимает настоящий Postgres на testcontainers и запускает
параллельные `POST /sales`. Тесты падают, если появятся два 201 на одну единицу товара
или баланс уйдёт в минус.
